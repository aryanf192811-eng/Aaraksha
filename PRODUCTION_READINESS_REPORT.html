Findings Summary what changed before this build was frozen

Beyond the documented API test suite, the backend was subjected to targeted adversarial and concurrency testing across seven categories: rate limiting, SQL injection, XSS, large payloads, concurrency, transaction rollback, and external-service failure. Five real defects were found and fixed against the live server — not just reviewed in code. Everything below was re-verified with a full Postman/Newman pass afterward.

Fixed — found via live testing
Fixed

SOS double-resolve race condition

sos.repository.js's updateStatus() had no status guard: two concurrent PATCH /govt/sos/:id/resolve requests on the same SOS both returned 200, and the second write silently overwrote the first responder's resolution notes with no error surfaced to either caller. Reproduced with two parallel requests against a live SOS before the fix (both 200); fixed with an atomic WHERE status NOT IN ('RESOLVED','FALSE_ALARM') guard at the DB layer, plus the same guard's result now distinguishes "not found" from "already closed" in both the govt and tourist resolve paths. Re-verified live: one request now gets 200, the other a clean 400 SOS_ALREADY_CLOSED.

src/repositories/sos.repository.js · src/services/govt.service.js · src/services/sos.service.js
Fixed

Auth rate limiter defined but never wired

express-rate-limit was configured (authLimiter, otpLimiter) but only generalLimiter and webhookLimiter were actually attached to any route — brute-force protection on /login was a no-op. Fixed by wiring dedicated limiters onto all six auth-sensitive routes.

src/routes/auth.routes.js
Fixed

Shared rate-limit bucket across unrelated routes

Wiring the limiter surfaced a second bug: authLimiter and otpLimiter were each a single shared middleware instance, so their in-memory counters were shared across every route that used them. A full Postman/Newman run tripped it for real — a handful of registration attempts exhausted the budget and the unrelated /govt/login request three folders later got 429'd. Fixed by turning both into factories (createAuthLimiter(), createOtpLimiter()) so each of the 9 auth/OTP routes gets its own counter.

src/middleware/rateLimiter.js · src/routes/auth.routes.js
Fixed

Registration budget too tight for its risk profile

Every request against a rate-limited route counts, including recoverable validation and conflict errors (duplicate phone, duplicate govt ID, bad Aadhaar format). At the login-style budget of 5 per 15 minutes, a legitimate user correcting a few typos during signup could get locked out — not just an attacker. Registration and govt-registration now get a separate, more generous budget (20) while login, govt-login, and password reset stay at the tight brute-force default (5).

src/middleware/rateLimiter.js · src/routes/auth.routes.js
Fixed

Malformed phone input crashed with an unhandled 500

Zod validated phone length (10–15 chars) but not digit format. Testing a SQLi-shaped string (' OR 1=1 --) as a login phone reached normalizePhone() downstream, which threw a plain Error with no statusCode — the global handler fell through to a generic 500 instead of a clean 400. Fixed with a PhoneSchema that wraps the same normalizer in a Zod .refine(), applied across all six phone fields in auth and profile-update schemas.

src/validators/common.validator.js · src/validators/auth.validator.js · src/routes/tourist.routes.js
Verified safe — tested live, not just reviewed
Confirmed

SQL injection

' OR 1=1 --, DROP TABLE, and UNION SELECT payloads fired at login, search, and profile fields. All queries are parameterized end-to-end; payloads are either rejected by validation before reaching SQL or treated as inert literal values.

Confirmed

Transaction rollback

Deliberately forced a mid-transaction failure inside withTransaction() — a valid scam_reports insert followed by a checkins insert with a bogus foreign key. The first insert did not survive the rollback; row count before and after the failed transaction was identical. Atomicity holds under real failure, not just by code inspection.

Confirmed

External service failure (Twilio / Gemini / OWM)

All three are unconfigured in this environment, which is itself the test: SMS sends no-op with sent=false and never throw; Gemini packing-list generation falls back to a static offline checklist; OpenWeatherMap fetches return null and TSI calculation proceeds without the weather factor rather than failing the whole trip update. See external services.

Confirmed

Large payload handling

Express's 10MB body-size limit correctly rejects oversized JSON bodies before they reach any handler.

Noted for follow-up — not backend defects
Note

User text is stored unescaped

Notes, scam-report descriptions, and messages are persisted as-is. This is a JSON API with no server-side HTML rendering, so the real XSS surface is whichever frontend renders these fields — worth confirming none of the three portals bypasses React's default escaping (e.g. via dangerouslySetInnerHTML) when displaying them.

Note

No application-level array-size caps

Trip stops, packing checklist items, and similar arrays have no explicit max length — Express's 10MB body limit is the only backstop. A request with thousands of small entries would currently be accepted.

Note

Stack traces in error responses

Correctly gated behind NODE_ENV === 'development' in errorHandler.js — verified the gate itself works. Confirm the production deploy sets NODE_ENV=production via a real environment variable, not the committed .env default, before going live.

Database Schema 14 tables

Three clusters: tourist-owned safety data (tourists, trips, SOS, DMS, checkins, location), government operations (govt users, rescue teams, assignments), and shared reference/support data (destinations, weather cache, scam reports, inbound SMS, OTP verifications). Full column definitions live in src/migrations/001_initial_schema.js — this shows the relationships that drive query joins and cascade behavior.

API Dependency Graph layering + cross-service calls

Every one of the 45 endpoints follows the same layered chain (left). The graph on the right is the part that actually varies by feature — which services call into other services' repositories, and which touch the external side effects (SMS, sockets).

Authentication Flow JWT + RBAC + token-less guardian links

Two authenticated roles (tourist, govt) share one JWT scheme with a role claim; middleware re-fetches the user row on every request rather than trusting the token payload, so a deactivated account is locked out immediately, not just after token expiry. The Guardian Portal is a third, deliberately unauthenticated path — a long random token embedded in the URL, not a login.

Dead Man's Switch Lifecycle

A tourist sets an interval (15–480 minutes); the cron layer — not the tourist's client — is the source of truth for whether it fires. Two independent per-minute jobs cover the warning and the trigger, so a crashed client can't prevent the trigger from running.

SOS Lifecycle race-condition-safe as of this build

Three entry points converge on the same state machine: manual trigger from the tourist app, automatic trigger from an expired DMS, and offline trigger via inbound SMS. Closing transitions are now guarded atomically at the database layer — see the highlighted edge.

TSI Calculation Flow rule-based, 0–100

Travel Safety Index starts at 100 and only ever loses points. Per-stop risk uses the worst stop on the route, not an average — a single dangerous leg shouldn't get diluted by three easy ones.

Request → Response Pipeline

The full Express middleware chain, in registration order. Webhook routes get their own body parser (urlencoded, for Twilio's form-POST format) ahead of the general JSON parser.

Error Handling Flow

A single global handler classifies every thrown error into a response code — Postgres error codes are mapped explicitly rather than leaking raw DB errors to the client.

Transaction Boundaries

Every multi-table write that must succeed or fail as a unit goes through withTransaction() (BEGIN / COMMIT / ROLLBACK on a dedicated client). Six call sites use it; everything else is a single statement and doesn't need one.

Socket.IO Event Flow

Four room types, each scoped to who's allowed to see what: the govt dashboard gets everything safety-related, a tourist's own room gets only their own updates, and a guardian's room is keyed by their opaque tracking token rather than an account.

Background Cron Jobs node-cron, Asia/Kolkata

Three schedules, all timezone-pinned so "10 minutes before trigger" means the same thing regardless of server deploy region.

External Services Gemini · Twilio · OpenWeatherMap

All three are optional at runtime — the platform's core safety functions (SOS, DMS, check-ins) do not depend on any of them being configured or reachable. Verified live in this environment, where all three are unconfigured.

Known Limitations & Recommendations

Honest gaps that don't block a demo but are worth tracking before wider deployment.

  • Rate limiting is per-IP, in-memory (express-rate-limit's default store) — restarting the process clears all counters, and it won't coordinate across multiple server instances behind a load balancer. A Redis-backed store is the natural next step if this scales beyond a single node.
  • No application-level caps on array-shaped fields (trip stops, packing items) — see findings.
  • Frontend escaping of stored user text (notes, scam reports) should be spot-checked across all three portals — the backend correctly treats this as opaque data, but that only matters if nothing renders it as raw HTML.
  • Confirm NODE_ENV=production is set via real environment configuration at deploy time, not inherited from the committed .env default, so stack traces stay out of error responses.
